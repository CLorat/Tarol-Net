# Sagas and reactions: evaluation (step 9 design)

Evaluation of [sagas.md](../architecture/sagas.md): inventory of the old saga code, candidates for the saga model, the
dead letter, the generator's place, the claim and timeouts, measurements against PostgreSQL, the owner's answers, and
what PRs 9A–9C must do. **Design only**: this PR changes no package code. Probes and output:
[`probes/sagas/`](probes/sagas/), [`output.txt`](probes/sagas/output.txt), [`Claim/output.txt`](probes/sagas/Claim/output.txt).
Labels as in the [conventions](../architecture/conventions.md). Source of the old code: `CLorat/Tarol@6a62f81`.

## 0. Summary

* **The old saga code is a complete but separate engine** **[verified by reading]**: 5,456 lines (Sagas, Engine, an
  empty Hosting project, InMemory and Marten stores, a generator shipped as its own package, 78 test methods); its own
  event store, inbox, correlation index, outbox and serializer beside the aggregates'. 25 of 27 review findings confirmed,
  2 in part, one new (N1: a second start runs the start handler again). None of the ROADMAP Phase 4 goals is met.
  Nothing is ported; the lessons are kept (§1.8).
* **Decided model** (S-4, S-15): a saga is an **aggregate** whose steps are **reactions**; started load-or-create
  (`ILoads<T>`), correlated by id, timeouts are scheduled reactions, compensations are forward changes. No saga runtime,
  no saga generator, no saga store **[verified]** on both stores, JIT and Native AOT.
* **Reactions** (S-2, S-3, S-6, S-14): `[OnEvent<T>]` factories on changes, generated by the Changes generator as a
  public `GeneratedReactions.Set`, composed across assemblies, named by the change type (pinned to rename).
* **Worker** (C-9, S-5, S-7, S-10, S-13): claim → pipeline → complete; Conflict, NotFound and 422 retry with backoff
  1 s … 5 min, dead letter after 10 attempts into `outbox_dead`; poll 100 ms, NOTIFY opt-in. A real crash between the
  reaction's commit and `Complete` redelivers once and commits once **[verified]**.
* **Measured** (4 cores): 287 / 777 / 1,218 rows/s with 1 / 4 / 16 workers on many streams; commit → reaction p50
  489 ms (poll 1 s), 29 ms (poll 100 ms), 7.2 ms (NOTIFY), but NOTIFY costs writers 30 %; the shipped anti-join claim
  is O(backlog) (600 ms per claim behind 16 deep streams), a maintained head flag 0.04–0.2 ms **[verified]**.
* **Aspire** (D-15): an AppHost 13.6.5 runs on SDK 11 with a PostgreSQL resource and the worker, also as its Native AOT
  binary; the dashboard shows the reaction spans with their links **[verified]**. The worker publishes with 0 IL warnings.
* **Plan** (S-11, S-12): one new package `Tarol.Sagas`; three PRs: 9A reactions (Changes), 9B outbox (Persistence),
  9C worker and hosting (Sagas).

### 1.2 Programming model (old)

A saga was `partial class X : Saga<X>` with `When(message, …)` handlers returning a data-only `SagaStep`
(`Apply(evt)`, `Execute(change)`, `CompensateWith(c)`, `Schedule(msg, delay)`, `Complete()`, `Compensate()`, `Fail(v)`)
and `On(evt)` state methods (Saga.cs:131-152, SagaStep.cs:46-114). `[StartedBy]` derived a UUIDv5 id from the
correlation key (SagaInternals.cs:18-21); later messages found the saga through a correlation index that only grew
(SagaEngine.cs:58-90, 279-281). Changes went out through the saga's outbox to a user-supplied `IChangeDispatcher`; a
failed change came back as `ChangeFailed<T>`, unhandled → `Fail` → compensate (SagaOutboxProcessor.cs:87-97,
SagaEngine.cs:179-182). Time came from `SagaOptions.UtcNow` (SagaOptions.cs:14), the Marten store used
`DateTimeOffset.UtcNow` (MartenSagaStore.cs:249).

### 1.3 Engine and outbox (old)

Claim with a lease, per entry deserialize and deliver or dispatch, `Complete` in a separate call after the saga commit,
`attempts + 1`, dead letter at `MaxAttempts`, else retry with exponential backoff (SagaOutboxProcessor.cs:33-58).
**Lease ownership was not checked** on Complete/Retry/DeadLetter (:43, 52, 57). Concurrency conflicts retried with random
jitter (SagaEngine.cs:127). The worker swallowed exceptions; no `ILogger` anywhere (:149-152). The serializer was
AOT-safe only when every message was covered by a registered context, silently otherwise (SagaMessageSerializer.cs:82-106).

### 1.4 Tests (old)

Covered: lifecycle (start, steps, completion, compensation order, timeouts), delivery dedupe by message id, correlation,
registry/serialization, the in-memory store. **Not covered**: the Marten store, the generator's diagnostics, the outbox
worker, the dead-letter path, a user `ChangeFailed<T>` handler, `[SagaName]`, correlation on real Tarol events, a second
start with a new message id (N1), cancellation, AOT.

### 2.2 Dead letter (question 2)

DL-A (a `dead_at` column) and DL-B (an `outbox_dead` table, decided S-5) both passed the C-9 scenario: three retries
with growing backoff (0.97, 2.15, 4.57 s), buried at attempt 4, the next row of the stream then runs **[verified]**.

```sql
-- DL-A: bury in place; the claim filters dead_at IS NULL in the candidates and in the head rule
UPDATE tarol.outbox SET dead_at = $3, claim_id = NULL, lease_until = NULL, last_error = $4 WHERE id = $1 AND claim_id = $2;
-- DL-B: move; the claim is unchanged
WITH d AS (DELETE FROM tarol.outbox WHERE id = $1 AND claim_id = $2
           RETURNING id, tenant, reaction, type, stream_id, version, event_id, attempts)
INSERT INTO tarol.outbox_dead (id, tenant, reaction, type, stream_id, version, event_id, attempts, last_error, dead_at)
SELECT id, tenant, reaction, type, stream_id, version, event_id, attempts, $4, $3 FROM d;
```

| | DL-A | DL-B |
|---|---|---|
| claim SQL | gains two filters | unchanged |
| re-drive while a newer row of the stream waits | the old id is the head again: it runs first and blocks the newer row **[verified]** | a new row behind the newer one **[verified]** |
| outbox size | grows with dead rows | live rows only |
| with the head flag (S-8) | promotion must skip dead rows | the row is gone; promote as for `Complete` |

### 2.4 Claim plan (found while measuring, S-8)

The shipped O-2 anti-join (8C) scans waiting rows in id order until it finds `LIMIT` heads, so with few streams and
deep backlogs, or many future-due timeouts, every claim walks the backlog. Candidate H keeps a `head` flag:

```sql
CREATE INDEX outbox_heads ON tarol.outbox (due_at, id) WHERE head;
-- claim
SELECT o.id FROM tarol.outbox o
WHERE o.head AND o.due_at <= $1 AND (o.lease_until IS NULL OR o.lease_until <= $1)
ORDER BY o.due_at, o.id LIMIT $2 FOR UPDATE SKIP LOCKED;
-- complete: delete the head and promote the next row of its key, one statement (bury: the same after the move)
WITH d AS (DELETE FROM tarol.outbox WHERE id = $1 AND claim_id = $2 RETURNING tenant, type, stream_id, reaction)
UPDATE tarol.outbox o SET head = true FROM d
WHERE o.id = (SELECT min(n.id) FROM tarol.outbox n
              WHERE (n.tenant, n.type, n.stream_id, n.reaction) = (d.tenant, d.type, d.stream_id, d.reaction));
-- commit: INSERT … head = NOT EXISTS (live row of the same key), the first row per key of this commit only
```

Race **[unverified]**: a commit inserting a row of key K while a worker completes K's head could each miss the other
(the insert sees the old head, the promotion does not see the uncommitted row) and leave K without a head. Commits of
one stream are already serialized by the guarded `UPDATE streams` (P-6); `Complete`/`Bury` must take `FOR SHARE` on
the same `streams` row so promotion and insert serialize too. PR 9B proves it with a race test (10–25 runs).

### 2.5 Timeouts (S-9)

T-1 keeps the head rule for scheduled rows: a shortened deadline (3 d → 1 d) fired at +3 d **[verified]**. T-2 (decided)
exempts reactions with `DueAt` from the head rule: it fired at +1 d and the 3-day row later was a stale no-op
**[verified]**. With H, T-2 is "scheduled rows are always heads".

## 4. Measurements **[verified]** ([`output.txt`](probes/sagas/output.txt); 4 cores, PostgreSQL 17.12 in local Docker)

### 4.1 Throughput (Release, JIT; each row: claim → load the auction → append one event → complete; batch 32)

| streams × rows | 1 worker | 4 workers | 16 workers |
|---|---|---|---|
| 2,000 × 1 | 287 rows/s | 777 rows/s | 1,218 rows/s |
| 16 × 125 | 237 rows/s | 426 rows/s | 370 rows/s |

Many streams scale until the database is the limit (4 cores). Deep backlogs on few streams are capped by the head
rule (16 in flight at most, by design) and then degrade with more workers: every claim walks the backlog (§4.4).

| trigger | commits/s |
|---|---|
| none | 2,429 |

## 5. Found while probing

1. **NU1510 for `Microsoft.Extensions.Hosting.Abstractions`**: .NET 11's `Microsoft.NETCore.App` ships it with the DI,
   logging and options abstractions; `BackgroundService` needs no package reference **[verified]**.
2. **The anti-join claim is O(backlog)** (§4.4); 8C's tests had 5 rows per stream, so it did not show.
3. **A shortened deadline waits behind the old one** under the head rule (§2.5).
4. **A Conflict for "already done" dead-letters a healthy saga**: the first `Expire` returned
   `Error.Conflict("Settlement.NotDue")` for a stale timeout, and a creation-start would answer a restart with
   `Settlement.AlreadyExists`. Both are Success in the decided rules (S-9, S-15).
5. **`nameof` inside an attribute on a change whose member is named like its type** (`Id<Settlement> Settlement`) binds to
   the member: CS1061; qualify the type (`nameof(ArtFlow.Settlement.DeadlineSet.DueAt)`). The skill says so.
6. **The generated namespace collides with a user type named like the assembly's first segment**: assembly
   `Probe.Sagas.App` → `namespace Probe.Sagas.App` for `GeneratedChanges` vs a top-level class `Probe` → CS0101 (7B code).
   9A emits `GeneratedReactions` in the same namespace and adds a note (or a diagnostic) for it.
7. **A stored state member of type `List<string>`** needs `[JsonSerializable(typeof(List<string>))]`; the store's
   exception says exactly that (P-12 path working as designed).
8. **`Activity.Current` is what the store writes**: a producer activity that no listener samples is `null`, so its
   events carry no `traceparent` and reactions have nothing to link to (the probe's own source-name typo showed it).
9. **Rows of a removed or renamed reaction** dead-letter with a clear message after N attempts (S-14).

## 6. Generator and diagnostics (9A)

### 16.2 Deliberate differences from §6, §7 and §12

* **No TCHG009**: TCHG005 already warns for every change with ruled members that is not `IValidatable`, reactions
  included; a second id for the same fact would only duplicate it.
* **`ReactionSet` takes the scheduled names explicitly** (`IsScheduled`), because 9B's claim needs them (S-9) and the
  schedule delegate alone cannot list them.
* **`Context`/`Options` are static members of `ReactionSet`**, so the generated code and later workers share one
  definition of the reaction's operation and key.
* **The switch dispatches on (name, event type)** in descending inheritance depth of the event; an event subtype with its
  own reactions does not also run its base type's (events are sealed records in practice).
* **The generated namespace collision** (§5 item 6) is unchanged: `GeneratedReactions` lives where `GeneratedChanges`
  lives. A diagnostic for it is left for the next generator change that touches both.
* The store does not use `ReactionSet` yet: 9B switches `NpgsqlStoreOptions.Reactions` to it; until then pass
  `GeneratedReactions.Set.Table`.
